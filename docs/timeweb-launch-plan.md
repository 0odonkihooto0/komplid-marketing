## Этап 2 — S3 для заявок

На App Platform контейнер эфемерный: «каждый новый деплой запускает новое
окружение, то есть создаётся новый Docker-контейнер, в котором не сохраняются
данные из предыдущих версий контейнера». Файл на диске не переживёт ни одного
деплоя, поэтому база заявок живёт в объектном хранилище.

**2.1. Бакет — ✅ создан 21.08.2026.** Регион **ru-1** (Санкт-Петербург),
доступ приватный. Имя бакета `bb41005d-0001-419e-8ae1-aee42b847ea0`,
адрес `https://s3.twcstorage.ru`.

**2.2. Ключи — ✅ выписаны.** Access key и Secret key лежат в `.env.local`
на машине владельца (файл в git не попадает) и задаются переменными в панели
App Platform на этапе 4.4. В репозиторий их не коммитим.

**2.3. Переменные приложения:**
```
S3_ENDPOINT=https://s3.twcstorage.ru
S3_REGION=ru-1
S3_BUCKET=bb41005d-0001-419e-8ae1-aee42b847ea0
S3_ACCESS_KEY=<из панели хранилища>
S3_SECRET_KEY=<из панели хранилища>
LEADS_ADMIN_TOKEN=<любая длинная строка>
```
Если `S3_BUCKET`, `S3_ACCESS_KEY` или `S3_SECRET_KEY` пусты, код молча
переключается на запись в файл — на App Platform это означает потерю заявок
при первом же деплое. Поэтому после первого деплоя проверить, что объекты
в бакете появляются (этап 8).

**Раскладка в бакете** — три ключа:
```
leads/events/{время}-{uuid}.json   история: по объекту на каждую отправку
leads/contacts/{sha256}.json       по объекту на уникальный контакт
leads/zayavki.xlsx                 таблица-зеркало, читаемая человеком
```
Счётчик оставшихся мест на главной считает ключи в `contacts/`. Дозаписи в S3
не бывает, поэтому один общий файл не годится: при двух одновременных заявках
одна была бы потеряна.

**2.4. Таблица заявок — XLSX в том же бакете.**
Разбирать объекты JSON руками неудобно, поэтому поверх хранилища лежит зеркало:
`leads/zayavki.xlsx` дополняется строкой при каждой заявке. Чтобы посмотреть —
зайти в панель хранилища Timeweb и скачать файл; открывается в Excel, LibreOffice
и Яндекс Документах. Колонки: дата и время (МСК), почта, телефон, имя, компания,
роль, откуда пришёл, ранний доступ, согласия и редакция политики, прочее.

Внешний сервис для этого не нужен и не используется: данные не покидают бакет,
отдельного токена не требуется, а обещание «данные в РФ» из подвала каждой
страницы и пункта 10.2 оферты остаётся верным без оговорок.

Строка пишется уже после ответа пользователю (`after` из next/server), поэтому
форма не ждёт загрузки файла. Дозаписи в объект S3 не существует — файл
читается, дополняется и кладётся целиком; при двух одновременных заявках строка
в таблице может потеряться, в `leads/events/` обе на месте. Починка:

```bash
curl -X POST https://komplid.ru/api/leads-sheet -H 'Authorization: Bearer <LEADS_ADMIN_TOKEN>'
```

Роут читает все заявки из бакета и перезаписывает таблицу целиком. Без
заданного `LEADS_ADMIN_TOKEN` он отвечает 404.

> Почему не Google Sheets: заявки — персональные данные, а часть 5 статьи 18
> 152-ФЗ требует вести их запись, накопление и хранение в базах на территории РФ.
> Google Sheets потребовал бы отдельного уведомления Роскомнадзора
> о трансграничной передаче и снятия обещания «данные в РФ» с сайта.

**Проверено 21.08.2026** на живом бакете: заявка через `/api/lead` кладёт объекты
в `events/` и `contacts/`, таблица создаётся и дополняется второй строкой не
затирая первую, кириллица в именах и названиях компаний сохраняется, пересборка
через `/api/leads-sheet` собрала 4 строки, без токена роут отвечает 401.
Тестовые объекты из бакета удалены — счётчик мест снова показывает 100.

**Готово, когда:** бакет создан, приватный, ключи выписаны; при желании —
получен токен Диска.

## Этап 4 — Приложение в App Platform

**4.1. Создать приложение.** Панель → App Platform → создать → тип **Dockerfile**.
Платформа читает `EXPOSE` из нашего `Dockerfile` (порт 3000) и сама поднимает
контейнер.

**4.2. Подключить репозиторий.** GitHub → `komplid-marketing`, ветка `main`.
**Автодеплой оставить выключенным**: в проекте выкат — явное действие
(`CLAUDE.md` §9), запускается кнопкой в панели. Репозиторий тяжёлый: рабочая
копия около 600 МБ, из них 354 МБ — статика корпуса СП. Первая сборка идёт долго.

> **Проверить до первого деплоя.** Документация App Platform упоминает
> ограничения по размеру репозитория, размеру образа, времени и памяти сборки,
> но конкретных цифр не публикует. С нашими 600 МБ это первый кандидат на отказ:
> спросить поддержку Timeweb заранее. Если корпус не проходит по лимиту —
> либо запасной путь на VDS (ниже), либо вынос `public/normativ/**` в S3
> с раздачей через rewrite. Второе — отдельная работа, в этот запуск не входит.

**4.3. Конфигурация.** Регион — **РФ**. Тариф — минимальный, которого хватает
на сборку Next.js; при падении сборки по памяти брать следующий.

**4.4. Переменные окружения.** Задать в панели приложения:

| Переменная | Нужна на | Что будет, если пусто |
|---|---|---|
| `S3_BUCKET`, `S3_ACCESS_KEY`, `S3_SECRET_KEY` | рантайме | **заявки уйдут в файл и пропадут при деплое** |
| `S3_ENDPOINT`, `S3_REGION` | рантайме | подставятся `s3.twcstorage.ru` и `ru-1` |
| `NEXT_PUBLIC_YANDEX_METRIKA_ID` | сборке | Метрика не подключится |
| `NEXT_PUBLIC_YANDEX_VERIFICATION`, `NEXT_PUBLIC_GOOGLE_VERIFICATION` | сборке | нет meta-подтверждения; не нужны, если подтверждать домен TXT-записью |
| `NEXT_PUBLIC_WAITLIST_MODE` | сборке | режим пре-лонча остаётся включённым — на старте это и нужно |
| `COMPANY_*` | сборке | подставятся настоящие значения из `src/lib/company.ts` |
| `INTERNAL_API_URL`, `INTERNAL_API_TOKEN` | рантайме | пересылка заявок в приложение молча пропускается |
| `TELEGRAM_BOT_TOKEN`, `TELEGRAM_CHAT_ID` | рантайме | уведомлений о заявках не будет |
| `LEADS_DATA_DIR` | рантайме | **не задавать**: файловый режим на этой платформе не нужен |

> Доходят ли переменные панели до этапа `docker build`, документация прямо
> не говорит. Сделано так, что это не критично: реквизиты ИП лежат значениями
> по умолчанию в коде, `NEXT_PUBLIC_SITE_URL` и `NEXT_PUBLIC_APP_URL` кодом
> не читаются вовсе, режим пре-лонча включён по умолчанию. Единственное, что
> обязано попасть именно в сборку, — идентификатор Метрики: если после первого
> деплоя счётчика на странице нет, значит переменные приезжают только в рантайм.

**4.5. Первый деплой.** Запустить сборку, смотреть журнал. Что бывает:
- сборка убита по памяти — взять тариф выше;
- ошибка клонирования или превышение лимита — упёрлись в размер репозитория (см. 4.2);
- контейнер поднялся, но отдаёт 502 — смотреть журнал приложения, обычно не хватает переменной.

**Готово, когда:** приложение открывается по техническому домену платформы.

**Выполнено 21.08.2026.** Сборка на стороне платформы заняла ~7 минут
(19:44 клон → 19:52 «Build succeeded»), образ поднялся с первого раза.
Платформа сама нашла порт: «Found 1 HTTP ports: ['3000/tcp']» — `EXPOSE 3000`
из `Dockerfile` читается, отдельная переменная порта не нужна. Проверка
здоровья прошла за 15 секунд, «Deploy succeeded» в 19:53.

Тип приложения — **Dockerfile, не compose**: `docker-compose.prod.yml` задаёт
`LEADS_DATA_DIR=/data` с томом, и на эфемерном контейнере это молча увело бы

(19 воркеров на 20 ядрах); на 2 vCPU воркеров меньше и пик ниже, но 1 ГБ мало.
Итоговый образ — **1,3 ГБ**, клон репозитория ~570 МБ.

Единственное предупреждение в журнале приложения: AWS SDK v3 требует
Node ≥ 22 для обновлений после первой недели января 2027, а в образе Node 20.
Не ошибка, но базовый образ стоит поднять до `node:22-alpine` отдельной задачей.

> 12 728 картинок корпуса СП идёт через Node. Пока трафика нет — не проблема.

**Готово, когда:** `https://komplid.ru` открывается с валидным сертификатом.

и `www.komplid.ru` смотрят на 37.77.105.205, сертификат Let's Encrypt выпущен

имя `komplid.ru` — TLS-рукопожатие обрывалось, и посетитель получал ошибку

· в панели — `www.komplid.ru` добавлен вторым доменом приложения, платформа
  выпустила на него отдельный сертификат (здесь на каждый домен свой, общего SAN нет);
· в коде — редирект `www → apex` в `next.config.mjs` через
  `has: [{ type: 'host' }]`, влит в `main` в PR #52.

Порядок был важен: до выпуска сертификата редирект бесполезен, TLS рвётся
раньше HTTP.

Редирект проверен на прод-сборке локально (`next start` + заголовок `Host`):
корень, вложенный путь и путь корпуса СП уходят одним 308-м на `https://komplid.ru`,
query сохраняется, apex при этом отдаёт 200 и не редиректится.

**Подтверждено на живом домене 22.08.2026** владельцем:
`curl.exe -sSI https://www.komplid.ru/` → `308` и `Location: https://komplid.ru`
(рукопожатие прошло, значит сертификат на www выпущен), а
`curl.exe -sSI https://komplid.ru/` отдаёт `Strict-Transport-Security: max-age=31536000` —
то есть новый билд на проде. Рядом с `Location` Next кладёт дублирующий
`Refresh: 0;url=…` — штатное поведение, браузеры идут по `Location`.

Проверять приходится с машины владельца: из веб-сессии агента `komplid.ru`
режет egress-политика, туда не доходят ни curl, ни fetch. В PowerShell важно
звать именно `curl.exe` — голый `curl` там алиас на `Invoke-WebRequest`
с другими ключами.

Отдельно: заголовка `Strict-Transport-Security` веб-сервер платформы не ставит
(на VDS его добавлял бы nginx). Добавлен в `next.config.mjs` (PR #51), локально
отдаётся — `max-age=31536000`. `includeSubDomains` не включать, пока
app.komplid.ru не поднят с валидным TLS.

## Запасной путь: собственный VDS

Актуален, если корпус СП не проходит по лимитам App Platform. Всё для него
в репозитории есть и поддерживается в рабочем состоянии.

Кратко: VDS 2 CPU / 2 ГБ в РФ, Ubuntu 24.04, пользователь `komplid`, файрвол
на 22/80/443, **swap 4 ГБ обязателен** (`next build` на 2 ГБ падает по памяти),
Docker с ротацией логов. Дальше — deploy-ключ GitHub, клон репозитория,
`.env.production` с `chmod 600`, запуск
`docker compose --env-file .env.production -f docker-compose.prod.yml up -d --build`,
nginx как reverse proxy на `127.0.0.1:3100`, сертификат через `certbot --nginx`,
HSTS включать последним. Заявки в этом варианте можно оставить в S3 или вернуть
на диск: том `leads` в `docker-compose.prod.yml` для этого и объявлен.

Выкат после настройки — `./deploy.sh` с локальной машины.

## Этап 10 — Эксплуатация

**10.1. Бэкап заявок — важнее бэкапа кода.** Код есть в GitHub, база заявок —
только в бакете. Настроить регулярную выгрузку любым S3-клиентом, например:

```bash
# rclone с настроенным remote на бакет Timeweb
rclone sync komplid-s3:<бакет>/leads /home/backup/komplid-leads-$(date +%F)
```

В архиве персональные данные: права 600, хранить в РФ, старые копии удалять
по сроку хранения из политики конфиденциальности.

**10.2. Мониторинг.** Внешняя проверка `https://komplid.ru/` и
`https://komplid.ru/api/waitlist-seats` раз в 5 минут (любой uptime-сервис).
Второй адрес важнее: он отвечает `{"left":N}` только если хранилище читается.
Если счётчик вдруг показывает ровно 100 свободных мест при собранных заявках —
это признак того, что S3 недоступен или ключи протухли.

**10.3. Журналы приложения** смотреть в панели App Platform. Ротацию платформа
берёт на себя.

**10.4. Обновления зависимостей.** `npm audit` раз в месяц. На момент запуска
известны уязвимости libvips, тянущиеся транзитивно через `sharp`; их закрытие
требует обновления Next.js вне текущего диапазона версий — делать отдельной
задачей, а не перед выкатом.

## Найдено проверкой 22.08.2026

Проверка после закрытия `www` прошла по всему чек-листу. Три пункта не закрыты.

**1. OG-превью нет на 54 страницах из 97** (все калькуляторы, все шаблоны,
посадочные `/pto`, `/prorab`, `/smetchik`, хабы `/shablony`, `/kalkulyator`,
`/normativ`). Главная и статьи блога превью отдают.

Причина — не опечатка, а правило Next.js Metadata API: объекты метаданных
сливаются **поверхностно**. Страница, объявившая свой `openGraph` без `images`,
не наследует картинку от корневого layout, а заменяет весь блок целиком.
Ровно это и сделано в восьми файлах: `pto`, `prorab`, `smetchik`,
`kalkulyator/page`, `kalkulyator/[slug]`, `shablony/page`, `shablony/[slug]`,
`normativ/page`.

Бьёт по каналу распространения: ссылка на посадочную в Телеграме или в чате
уходит без карточки. Чинится строкой `images` в каждом из восьми файлов.

**2. Lighthouse: десктоп 100, мобильный 66** (прогон по прод-сборке в контейнере
агента). Десктоп — LCP 0.8 с, TBT 0 мс, CLS 0.004. Мобильный пресет даёт
LCP 4.5 с и TBT 680 мс, но он же эмулирует четырёхкратно замедленный процессор
поверх и без того слабого контейнера, так что цифра — ориентир, а не приговор.
Мерить надо PageSpeed Insights по живому адресу; целевые 90 из плана пока
не подтверждены.

**3. `npm audit` в прод-зависимостях: 7 пакетов, 5 high.** Главный —
сам `next@16.2.4`, за которым числятся 22 записи, среди них обход middleware
в App Router и SSRF в rewrites через подставной хост назначения. У нас есть
и middleware (`/ref/[code]`), и rewrites (корпус СП), так что оба сценария
не теоретические. Фикс — `next@16.3.2`, **мажор не меняется**; план раньше
исходил из того, что закрытие требует выхода за диапазон версий, — это больше
не так. Остальное: `sharp`/libvips, `postcss`, `js-yaml`, `nanoid`, `uuid`.
Обновление Next требует пересборки и повторной приёмки — отдельной задачей,
но раньше остальных.

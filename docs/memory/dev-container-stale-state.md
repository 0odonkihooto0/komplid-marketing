`docker compose up` может показывать сайт, собранный до `git pull`: страница открывается,
но часть стилей или зависимостей старые. Выглядит как дефект кода, ищется часами.

Две независимые причины, дающие один симптом:

1. **Тома Compose переживают пересоздание контейнера.** Анонимные тома
   (`- /app/node_modules`) переносятся в новый контейнер, а не создаются заново, —
   ни `up`, ни `--build` их не обновляют. После смены `package-lock.json` внутри
   остаются прежние пакеты. Чистит только `down -v` или `--renew-anon-volumes`.
2. **Кэш Turbopack не замечает правок, сделанных при остановленном сервере.**
   Проверено 18.08.2026 на `src/styles/globals.css`: приписанные правила не попали
   в отдаваемый CSS-чанк, новые секции главной приехали без стилей, появились только
   после удаления `.next`. При этом кэш, испорченный упавшей сборкой, инвалидируется
   нормально — проверялось отдельно, и первый вывод «дело не в кэше» был неверным.

**Why:** обе причины бьют в один симптом, который читается как «сайт не соответствует
тому, что присылали», и уводит поиск в код, где дефекта нет.

**How to apply:** тома названы (`komplid_node_modules`, `komplid_next_cache`),
`docker/dev-entrypoint.sh` при старте сверяет контрольную сумму `package-lock.json`
с записанной в томе и чистит кэш сборки. Ручной вариант, если всё же залипло, —
`docker compose down -v && docker compose up --build`; он же в `README.md`.

Отдельно: `docker-compose.yml` требует `env_file: .env.local`, а файл в `.gitignore` —
без `cp .env.example .env.local` контейнер не стартует вовсе.

`distDir` абсолютным путём проблему не решает: Next разрешает его относительно корня
проекта, и `/tmp/next-dev` превращается в `<проект>/tmp/next-dev`, то есть в тот же
примонтированный каталог.

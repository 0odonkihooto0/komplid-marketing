В dev-режиме Next.js **не гидратирует страницу, если не установился HMR-вебсокет**
(`ws://<хост>:3200/_next/webpack-hmr`). React не монтируется, обработчики не
навешиваются: не работают ни табы главной, ни переключатель темы, ни бургер,
ни формы. Разметка и стили приходят с сервера, поэтому страница выглядит
правильной — и дефект читается как «сломаны только табы».

Проверено 18.08.2026 подменой `window.WebSocket` на всегда падающий:

| Режим | WS живой | WS мёртвый |
|---|---|---|
| `next dev` (Turbopack) | гидратация есть | **гидратации нет** |
| `next dev --webpack` | гидратация есть | **гидратации нет** |
| `next start` (прод-сборка) | гидратация есть | **гидратация есть** |

Смена сборщика не помогает — вебсокет нужен обоим dev-режимам. Прод-сборка
HMR-клиента не содержит и от обрыва не страдает.

**Why:** симптом неотличим от дефекта вёрстки или логики, и уводит в отладку
исправного кода. У владельца проекта (Windows + Docker Desktop) это съело две
сессии: код был корректен и проходил tsc, тесты и сборку.

**How to apply:** признаки — в консоли браузера `WebSocket connection … failed`,
проверка гидратации возвращает `false`, при этом чанки в Network отдаются 200/304.
Быстрый серверный признак: в логе `next dev` после каждой загрузки главной должен
появляться `GET /api/waitlist-seats` — его шлёт `SeatsCounter` из `useEffect`.
Нет этого запроса при нескольких `GET /` — гидратации нет.

Порядок разбора: открыть `http://127.0.0.1:3200` вместо `localhost` (на Windows
`localhost` резолвится в IPv6 `::1`, публикация порта Docker слушает IPv4; HTTP
откатывается на IPv4, апгрейд до WebSocket — часто нет), затем брандмауэр и
антивирус, затем системный прокси. Запасной путь без вебсокета —
`docker compose -f docker-compose.preview.yml up --build`: та же прод-сборка,
но с `.env.local`, на порту 3200.

См. также [[dev-container-stale-state]] и [[branch-not-merged-symptom]] — две
другие ловушки окружения, дававшие похожее «сайт не соответствует коду».
